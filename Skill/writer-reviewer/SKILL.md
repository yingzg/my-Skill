# Writer-Reviewer 自动循环工作流

开发Skill，模拟真实开发中「编码 → 自审 → 提审 → 修复」的质量保障流程。Writer（主 Agent）完成编码和自审，Reviewer（子 Agent）独立审查，通过双层循环确保交付质量。

| 循环 | 角色 | 退出条件 | 次数限制 |
|------|------|---------|---------|
| 内循环（自审） | Writer 自行审查并修复 | 一轮审查未发现新问题 | 无限制 |
| 外循环（提审） | Reviewer 独立审查，Writer 修复 | Reviewer 无阻塞问题 | 最多 3 轮 |

---

## Phase 0: 提炼任务摘要

本 Skill 被激活时，用户与 Writer 通常已经过多轮沟通澄清需求。Writer 需从当前对话上下文中提炼一份结构化的「任务摘要」。此摘要贯穿整个工作流，作为自审和 Reviewer 审查的统一判断基准。

输出格式：

```
### 任务摘要
- **目标**：一句话描述本次要实现什么
- **验收标准**：列出可检验的完成条件（2-5 条）
- **约束**：技术栈限制、兼容性要求、性能指标等（如有）
```

### 验收标准编写规范

验收标准是**用户视角的业务结果**，回答的是「做完之后用户能看到什么效果」，而不是「开发者要怎么实现」。

**核心判断法**：把这条标准念给一个不懂代码的产品经理听，他能理解吗？能 → 业务结果；不能 → 实现细节。

#### 禁用词表（出现即判定为实现细节，必须改写）

以下内容出现在验收标准中时，100% 是实现细节：
- **类名/方法名/变量名**：`BatchRerunRequest`、`selectPhotosForRerun`、`batchInsertIgnore`、`copyDetectionResult` 等
- **表名/字段名/SQL关键词**：`file_ai_check`、`ai_check_version=2`、`INSERT ON DUPLICATE KEY UPDATE`、`GROUP BY`、`JOIN` 等
- **具体数值/策略**：分批200条、游标分页500条、10QPS限流、Redis锁4小时、最多3轮重试 等
- **技术方案描述**：用 UPDATE JOIN 代替 INSERT ON DUPLICATE、去掉分流查询、统一用 INSERT IGNORE + UPDATE 等

#### 正确 vs 错误对照

| 错误（实现细节） | 正确（业务结果） |
|-----------------|-----------------|
| `copyDetectionResult` SQL 从 INSERT ON DUPLICATE KEY UPDATE 简化为 UPDATE JOIN | 结果同步的代码简洁易读 |
| 去掉 `selectExistingImageIds` 分流查询，统一用 INSERT IGNORE + UPDATE | 记录准备逻辑简洁，不做多余查询 |
| `file_ai_check` 记录被重置且 `ai_check_version=2` | 重跑后照片的AI检核结果被正确更新 |
| 新增 `BatchRerunRequest` DTO，含 countryCodes、startTimeUtc 参数 | 提供一个接口，输入国家列表和日期范围即可触发重跑 |
| 分批200条更新DB，游标分页500条查询 | 大数据量下不会OOM或超时 |
| 调用 `aiCheckHttpClient.sendAiCheck()` 按国家分组 | Dify和Python双线检测均被正确触发 |
| 清理 `java.util.concurrent` 全限定类名 | 代码无全限定类名 |

#### 输出前强制自检流程（MUST DO，不可跳过）

每条验收标准写完后，**逐条执行**以下检查，任一条命中则必须改写：

1. **禁用词扫描**：是否包含类名、方法名、表名、字段名、SQL 片段、具体数值？→ 命中则改写
2. **产品经理测试**：不懂代码的人能否理解这条标准？→ 不能则改写
3. **"怎么做"测试**：这条标准是在描述"做什么/效果是什么"还是"怎么做/用什么技术"？→ 后者则改写
4. **溯源测试**：这条标准对应用户说过的哪句话？→ 找不到对应则可能是凭空添加，删除或与用户确认

规则：
1. 将多轮对话中的需求讨论浓缩为上述结构，不遗漏用户明确提出的要求
2. **验收标准必须通过上述 4 项自检**，不通过不得输出
3. 输出任务摘要后**暂停，等待用户确认**再进入 Phase 1
4. 用户确认后，任务摘要冻结，后续流程中不再修改（除非用户主动要求调整）

## Phase 1: Writer 编码

按任务摘要的目标和验收标准完成编码。编码完成后进入 Phase 2。

---

## Phase 2: Writer 自审循环（内循环）

编码完成后，进入自审循环。每轮自审按以下检查清单逐项审查本次改动的所有文件。

### 自审检查清单

| # | 维度 | 审查要点 |
|---|------|---------|
| 1 | **需求符合** | 逐条对照任务摘要的验收标准，确认每条均已满足 |
| 2 | **正确性** | 边界条件、空值处理、异常路径、类型安全 |
| 3 | **一致性** | 命名风格、错误处理模式、日志规范是否与项目现有代码一致 |
| 4 | **遗漏** | 是否有遗漏的边缘场景、缺失的输入校验、未处理的错误分支 |
| 5 | **可读性** | 函数长度、嵌套深度、注释是否充分（非显而易见的逻辑） |

### 自审流程

1. 用 `git diff` 或逐文件 Read 审查本次所有改动
2. 按检查清单逐维度审查，记录发现的问题
3. **如发现问题**：修复代码，然后重新执行步骤 1（开始新一轮自审）
4. **如一轮审查未发现任何新问题**：自审通过，输出自审摘要，进入 Phase 3

### 自审摘要格式

自审通过后输出（仅供 Writer 自己记录，不传递给 Reviewer）：

```
自审通过。内循环共 N 轮，累计修复 M 个问题：
- [问题1简述] — 已修复
- [问题2简述] — 已修复
```

---

## Phase 3: Reviewer 独立审查（外循环）

自审通过后，进入外循环。初始化轮次计数器 `review_round = 1`。

### 3.1 Spawn Reviewer

每轮审查**必须**用 Agent 工具 spawn 一个全新的 Reviewer 子 Agent。按以下 prompt 模板填充实际内容后传入：

#### Reviewer Prompt 模板

```
# Code Review 任务

## 业务诉求
{从 Phase 0 冻结的任务摘要原文粘贴，包括目标、验收标准、约束}

{以下区块仅在 review_round >= 2 时包含}
## 上轮 Review 意见及处理
| # | 上轮阻塞问题 | Writer 处理方式 |
|---|-------------|---------------|
| 1 | {问题描述} | {修复说明 / 不修复理由} |

## 审查指引

作为独立 Reviewer，请基于以上业务诉求，对本次代码改动进行全面审查。

**第一步：自行发现改动范围。** 使用 `git diff` 查看本次所有改动，了解改了哪些文件、改了什么内容。不要依赖 Writer 提供的文件列表——你需要独立判断改动范围是否合理、是否有遗漏。

**第二步：按以下维度审查（按优先级）：**
1. **实现思路**：Writer 选择的实现方案是否合理？有没有更简洁、更合适的方式？是否改对了地方？是否遗漏了该改的文件？
2. **需求符合**：对照验收标准，是否有未满足或理解偏差的条目
3. **正确性**：bug、边界条件、并发安全、异常处理
4. **设计合理性**：接口设计、职责划分、扩展性
5. **性能与资源**：N+1 查询、内存泄露、不必要的 IO
6. **安全性**：注入、敏感信息、权限校验

按以下固定格式输出审查结果，不要输出其他内容：

### 改动理解

先概述你对本次改动的理解：改了哪些文件、每处改动的目的是什么、整体实现思路是怎样的。这一节的目的是让 Writer 确认你是否正确理解了改动意图，避免后续建议基于误解。

### 阻塞问题（必须修复）

{如无则写"无"}

- **[B1]** `文件路径:行号` — 问题标题
  - 我的理解：你这样做是为了……
  - 问题：具体描述
  - 替代方案（可选）：如果是我来实现，我会……（说明具体方案及其优势。若认同当前思路只是实现有问题，此项省略）

### 建议（非阻塞，Writer 自行决定）

{如无则写"无"}

- **[S1]** `文件路径:行号` — 建议标题
  - 我的理解：你这样做是为了……
  - 说明：具体描述
  - 替代方案（可选）：如果是我来实现，我会……（说明具体方案及其优势。若认同当前思路，此项省略）

### 架构级问题（如有，需升级给用户决策）

{如无则写"无"}

- **[A1]** 问题描述及影响范围
```

### 3.2 处理 Reviewer 反馈

收到 Reviewer 输出后，按以下决策树处理：

```
Reviewer 输出
    │
    ├─ 无阻塞问题 → Phase 4（汇总报告）
    │
    └─ 有阻塞问题
         │
         ├─ review_round >= 3 → Phase 4（汇总报告，标注残留问题）
         │
         └─ review_round < 3
              ├─ 1. 逐条处理阻塞问题：修复代码或记录不修复理由
              ├─ 2. 建议类问题：自行决定是否采纳，记录决策
              ├─ 3. 架构级问题：记录，在 Phase 4 报告中升级给用户
              ├─ 4. 重新进入 Phase 2（内循环自审）
              ├─ 5. review_round += 1
              └─ 6. 回到 3.1 spawn 新 Reviewer
```

关键规则：
- 每轮修复后**必须重新进入 Phase 2 自审**，自审通过后才 spawn 新 Reviewer
- **只有阻塞问题触发下一轮**，纯建议不触发
- 架构级问题不阻塞流程，但必须在汇总报告中呈现给用户

---

## Phase 4: 决策、汇总报告 & 用户验收

工作流结束后（Reviewer 通过 或 达到 3 轮上限），按以下顺序执行：

### 4.1 用户决策

如有残留问题或架构级问题，先呈现给用户决策。

### 4.2 汇总报告

**严格按照 `report-template.md` 模板**输出汇总报告。

模板文件位置：与本 skill.md 同目录下的 `report-template.md`。

#### 报告输出规则

1. **所有层级必须有编号**，使用 `大章节.小节.子项` 体系（如 `3.1.2.1`），禁止无编号的裸标题或裸表格行
2. **表格每行必须有独立编号**，编号列为表格第一列
3. **外循环每轮的结构固定为**：修复（第 2 轮起）→ 内循环自审 → Reviewer 审查，三个子节缺一不可
4. **双方意见一致后，必须输出「Review 核心收获」**：整理 review 过程中最关键的发现、设计层面的改进、未采纳建议的共性、可带走的经验
5. **汇总报告必须包含「给用户 Review 的思路」**，帮助用户理解改动全貌，为用户自行 review 代码提供指引。内容包括：
   - **改动全景**：本次一共改了哪些文件，每个文件改了什么（一句话）
   - **审查顺序**：由外向内（先看调用入口，再看核心逻辑，最后看底层实现），或按业务流程顺序，说清楚先审什么、后审什么、为什么这个顺序
   - **每块改动的业务意义**：为什么要改这个文件、不改会怎样、改了解决什么问题
   - **重点关注项**：哪些改动风险最高、最容易出错、需要重点审查

### 4.3 用户 review 最终代码

汇总报告输出后，提示用户 review 最终代码，工作流结束

## MUST DO

1. Phase 0 输出任务摘要后**必须暂停等待用户确认**，不得自行跳过确认直接编码
2. **验收标准必须通过 4 项强制自检**（禁用词扫描、产品经理测试、"怎么做"测试、溯源测试），不通过不得输出。验收标准中出现类名、方法名、表名、字段名、SQL 片段、具体数值即判定不通过
3. 每轮 Reviewer **必须通过 Agent 工具重新 spawn**，禁止在主 Agent 上下文中模拟 Reviewer 角色
3. Reviewer prompt **仅传递业务诉求**（任务摘要）和上轮意见（第 2+ 轮），**不得包含改动文件列表、修改说明、自审过程**——Reviewer 必须通过 `git diff` 自行发现改动范围
4. 每轮修复后**必须重新进入 Phase 2 自审**，自审通过后才能 spawn 下一轮 Reviewer
5. Reviewer 输出**必须严格遵循指定格式**（阻塞问题 / 建议 / 架构级问题三区块），在 prompt 中明确要求
6. **只有阻塞问题触发外循环下一轮**，建议类问题记录但不触发
7. 外循环达到 3 轮上限时**必须停止并汇总报告**，将残留问题交由用户决策
8. 汇总报告**必须包含所有架构级问题**，不得遗漏
9. 汇总报告**必须严格按照 `report-template.md` 模板输出**，所有层级必须有编号（`大章节.小节.子项`），表格每行必须有独立编号

## MUST NOT DO

1. **不得在验收标准中写实现细节**——禁止出现类名、方法名、表名、字段名、SQL 片段、具体数值、技术方案描述。违反此规则等同于流程失败
2. **不得在主 Agent 中扮演 Reviewer**——必须通过 Agent 工具 spawn 独立子 Agent
2. **不得把自审细节、改动文件列表、修改说明传递给 Reviewer**——Reviewer 只接收业务诉求，自行通过 `git diff` 发现改动范围并独立判断实现方案
3. **不得跳过自审直接 spawn Reviewer**——内循环是外循环的前置条件
4. **不得在外循环中因建议类问题而触发新一轮**——只有阻塞问题才触发
5. **不得在 3 轮上限后继续循环**——必须停止并升级给用户
6. **不得省略汇总报告**——无论通过还是达到上限，都必须输出完整报告
7. **不得在 Reviewer 未读取文件内容的情况下输出审查意见**——prompt 中已要求 Read 文件
8. **不得输出无编号的报告**——所有标题、小节、表格行必须有层级编号，禁止裸输出
