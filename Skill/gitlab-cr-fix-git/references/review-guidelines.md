# 代码审查指南

审查 GitLab MR diff 时，按本指南确定优先级和评论质量标准。

## 高优先级文件

优先审查这些文件：

- `*Service.java`、`*ServiceImpl.java`、`*DomainService.java`
- `*Controller.java`、API 实现类
- repository、DAO、gateway
- mapper XML 和 SQL 文件
- 事务、鉴权、权限、支付、库存、数据写入路径

## 评论质量标准

有效评论必须满足：

1. 指向具体文件、方法或逻辑位置。
2. 说明明确的失败模式或回归风险。
3. 给出可执行的修复方向。
4. 避免重复已有 discussion。

应避免：

- 纯格式或纯风格评论
- 空泛建议
- 只为凑数量而生成的评论
- 未基于真实 diff 内容的问题

## 常见问题类型

| 分类 | 示例 |
|---|---|
| 正确性 | 缺少空值检查、边界判断错误、分支顺序错误 |
| 数据一致性 | 负库存、重复扣款、重复写入、缺少幂等 |
| 兼容性 | DTO 语义变化、返回类型不兼容、枚举行为变化 |
| 性能 | N+1 查询、循环 RPC/DB、缺少过滤条件、大范围扫描 |
| 安全 | 缺少鉴权、SQL 注入、敏感日志输出 |
| 测试 | 缺少分支测试、mock 依赖不匹配、断言脆弱 |

## 行级评论原则

1. 优先评论在新增或修改的可评论行上。
2. 如果问题无法稳定映射到 diff 行，不要默认降级为普通 MR 评论。
3. 评论正文应包含“问题、影响、建议”三部分。
4. 不要为了满足评论数量发布低价值评论。
5. 发布前必须检查已有 comments/discussions，避免重复反馈。
