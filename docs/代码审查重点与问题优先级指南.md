# AI 代码审查重点与问题优先级指南

> 用途：设计 code review 类 Skill、Agent、CLI 工具时，作为审查重点和输出优先级模板。

## 一句话原则

AI 代码审查不应该变成“代码风格点评”。高价值 code review 的目标是发现 **本次变更可能引入的真实工程风险**。

优先关注：

- 会不会引入线上 bug
- 会不会破坏已有行为
- 会不会造成数据错误
- 会不会带来安全风险
- 会不会导致性能退化
- 测试是否覆盖关键风险路径

默认降低优先级：

- 纯命名建议
- 泛泛的“建议增加注释”
- 无明确风险的代码风格建议
- 与本次变更无关的老问题
- 没有证据支撑的架构建议

## 审查对象：优先审查 diff，不要泛审全文件

如果用于 MR / PR 审查，AI 应优先审查本次变更。

推荐约束：

```text
只审查本次 diff 引入或触发的风险。
不要对未修改代码提出泛泛建议。
只有当未修改代码与本次变更发生交互并形成风险时，才可以指出。
```

原因：

- 泛审全文件容易输出大量历史遗留问题，开发者采纳率低。
- MR 审查的核心问题是“这次改动能不能合入”，不是“这个文件是否完美”。
- 评论应尽量定位到新增/修改行，方便开发者行动。

## 问题优先级

建议使用 P0 / P1 / P2 / P3，而不是只用 High / Medium / Low。P0/P1 更接近工程处理优先级。

| 优先级 | 含义 | 是否建议输出 |
|---|---|---|
| P0 | 必须修复，否则可能导致 bug、安全事故、数据错误、明显回归 | 必须输出 |
| P1 | 强烈建议修复，存在明确稳定性、性能、兼容性或测试风险 | 应输出 |
| P2 | 可维护性问题，但必须说明具体后果 | 谨慎输出 |
| P3 | 风格、命名、格式、偏好类建议 | 默认不输出 |

## P0：必须优先发现的问题

P0 是 code review 最有价值的部分。AI 应该把主要能力用在这里。

### 1. 逻辑正确性风险

重点检查：

- 条件判断是否反了
- 新增分支是否遗漏
- 默认分支是否合理
- 状态机流转是否完整
- 多个字段组合时是否有遗漏场景
- 新旧逻辑是否语义不一致
- 重构后行为是否变化

典型问题：

```text
新增了 storeType 维度，但重复校验只比较了 userTitle，没有比较 storeType，可能导致不同门店类型的规则被误判为重复。
```

输出要求：

```text
说明哪个输入场景会触发、当前代码会怎么走、正确行为应该是什么。
```

### 2. 空值、边界值、异常路径

重点检查：

- 入参是否可能为 null / empty
- 列表是否可能为空
- 下标访问是否越界
- map.get 后是否直接使用
- Optional / nullable 字段是否处理完整
- 异常路径是否吞掉关键信息
- 失败时是否留下半完成状态

典型问题：

```text
当 queryResult 为空时直接调用 get(0)，会在无数据场景触发 IndexOutOfBoundsException。
```

### 3. 数据一致性风险

重点检查：

- 写数据库是否在事务内
- 多表写入是否可能部分成功
- 重试是否幂等
- 唯一约束是否和业务唯一性一致
- 更新条件是否过宽
- 删除是否有租户、用户、业务范围条件
- 失败回滚是否完整

典型问题：

```text
先插入主表再插入明细表，但方法没有事务。明细插入失败时主表会残留脏数据。
```

### 4. 并发和幂等风险

重点检查：

- 是否存在重复提交
- 是否有并发创建重复记录
- 是否需要分布式锁
- 锁 key 是否包含足够业务维度
- 先查后写是否有竞态
- MQ / 定时任务 / 回调是否可能重复执行

典型问题：

```text
当前逻辑通过先查询后插入避免重复，但没有唯一索引或锁保护，并发请求下仍可能插入重复规则。
```

### 5. 安全风险

重点检查：

- SQL 注入
- 命令注入
- SSRF
- XSS
- 越权访问
- 敏感信息日志
- token / password / key 泄露
- 文件路径穿越
- 反序列化风险

典型问题：

```text
用户输入被直接拼接进 SQL order by 字段，攻击者可构造非法排序字段触发 SQL 注入。
```

### 6. 明显回归风险

重点检查：

- 方法签名变更是否影响调用方
- 返回值语义是否变化
- 默认值是否变化
- 枚举新增后旧逻辑是否兼容
- 配置项默认行为是否改变
- 老数据是否能兼容新逻辑

典型问题：

```text
新增枚举值后 switch 没有 default 处理，旧调用方传入新枚举时会返回 null，破坏原有接口约定。
```

## P1：强烈建议修复的问题

P1 问题不一定马上造成事故，但有明确工程风险。

### 1. 性能风险

重点检查：

- 循环中查数据库
- 循环中调用 RPC / HTTP
- 没有分页的大查询
- 大对象深拷贝
- 不必要的全表扫描
- 缺少索引条件
- 重复计算
- 锁粒度过大

典型问题：

```text
对每个门店逐个调用 queryRule，门店数量较大时会形成 N+1 查询，建议批量查询后按 storeId 分组。
```

### 2. SQL 风险

重点检查：

- WHERE 条件是否可能缺失
- UPDATE / DELETE 条件是否过宽
- LIKE 前缀通配是否导致索引失效
- ORDER BY 字段是否有索引
- JOIN 是否可能放大数据量
- 动态 SQL 最差路径是否可接受
- 是否缺少租户、国家、渠道等必要过滤条件

典型问题：

```text
动态 SQL 中 country 条件是可选的，当 country 为空时会扫描全部国家数据，建议在入口强制校验或补充默认范围。
```

### 3. 接口兼容性风险

重点检查：

- API 入参是否从可选变成必填
- 出参字段语义是否变化
- 字段类型是否变化
- 枚举是否新增但客户端未兼容
- 错误码是否变化
- 老版本客户端是否还能正常使用

典型问题：

```text
接口新增必填字段 dataChannel，但未提供默认兼容逻辑，旧客户端请求会失败。
```

### 4. 测试缺口

重点检查：

- 新增分支是否有测试
- 异常路径是否有测试
- 边界值是否有测试
- 数据为空时是否有测试
- 并发 / 幂等逻辑是否有测试
- bug fix 是否有回归测试

典型问题：

```text
本次修复的是空列表场景，但测试只覆盖了正常列表，缺少复现 bug 的回归用例。
```

输出测试问题时，最好给出具体测试场景：

```text
建议补充：
1. dataChannel 为 null 时使用默认规则
2. dataChannel 不同时不应判定为重复
3. dataChannel 为空列表时不应抛异常
```

### 5. 可观测性与排障风险

重点检查：

- 关键失败路径是否有日志
- 日志是否包含定位问题所需上下文
- 是否打印敏感信息
- 异常是否被吞掉
- 错误码是否能区分失败原因
- MQ / 定时任务是否有 traceId / bizId

典型问题：

```text
捕获异常后只返回 false，没有记录 ruleId 和 country，线上失败时无法定位是哪条规则处理失败。
```

## P2：谨慎输出的问题

P2 主要是可维护性问题。AI 不应输出泛泛建议，必须说明具体影响。

可以输出：

- 重复逻辑导致两个分支未来容易改漏
- 方法过长且已经影响业务规则理解
- 魔法值代表业务状态，容易误用
- 复杂条件缺少命名，导致审查者难以确认语义
- 多个概念混在一个类里，已经影响测试或复用

不建议输出：

- “建议优化命名”
- “建议增加注释”
- “建议拆分方法”
- “代码可读性可以提升”

除非能说明后果：

```text
这里的变量名 result 同时表示校验结果和最终保存结果，后续新增分支时容易误用。建议拆成 validateResult 和 saveResult。
```

## P3：默认不输出的问题

以下内容默认不要作为 review 发现输出：

- 纯格式问题
- 个人偏好的命名问题
- 没有上下文的“建议加注释”
- 没有实际风险的“建议抽方法”
- 与本次变更无关的历史遗留问题
- 已经由 formatter / linter / Sonar 自动检查的问题

除非项目明确要求：

```text
如果团队规范明确禁止某类写法，例如禁止 MyBatis Plus、禁止 @SpringBootTest、禁止直接测试 private 方法，则可以提升优先级。
```

## AI 审查输出格式

推荐每条问题使用固定结构，避免泛泛而谈。

```markdown
### P1: 循环内查询数据库导致 N+1 风险

- 位置：`RuleService.java:128`
- 类型：性能风险
- 触发条件：当门店数量较多时，每个门店都会单独调用 `queryRule`
- 影响：接口耗时随门店数量线性增长，可能拖慢批量导入或规则匹配
- 建议：改为批量查询规则后按 `storeId` 分组复用
- 置信度：高
```

必要字段：

- 优先级
- 位置
- 问题类型
- 触发条件
- 影响后果
- 修改建议
- 置信度

不推荐输出：

```text
这里可能有性能问题，建议优化。
```

原因：没有触发条件、没有影响范围、没有修改方向。

## AI 审查 Prompt 模板

可以直接用于 code review 类 Skill。

```text
你正在进行提交 MR 前的代码风险审查。

目标不是做代码风格点评，而是发现本次变更可能引入的真实工程风险。

请优先审查本次 diff 或用户指定代码中的以下问题：

P0 必须修复：
1. 逻辑错误、边界条件遗漏、空值异常、异常路径错误
2. 数据一致性问题：事务、幂等、重复提交、部分成功、并发更新
3. 安全问题：注入、越权、敏感信息泄露
4. 会导致线上故障或明显回归的问题

P1 强烈建议修复：
1. 性能风险：N+1 查询、循环调用外部服务、无分页、大对象复制
2. SQL 风险：最差路径扫描、UPDATE/DELETE 条件过宽、索引失效
3. API 兼容性风险：入参/出参语义变化、枚举/字段兼容问题
4. 测试缺口：新增关键逻辑没有对应测试
5. 可观测性问题：关键失败路径无法排查

P2 谨慎输出：
1. 会造成后续误改或漏改的可维护性问题
2. 已经影响测试、理解或复用的结构问题

默认不要输出：
1. 纯代码风格建议
2. 泛泛的“建议增加注释”
3. 没有明确风险的命名建议
4. 与本次变更无关的历史问题
5. formatter、linter、Sonar 已能自动发现的问题

每条问题必须包含：
- 优先级：P0/P1/P2
- 位置：文件名:行号
- 问题类型
- 具体问题
- 触发条件
- 影响后果
- 建议修改
- 置信度：高/中/低

如果没有 P0/P1 高价值问题，请明确说明“未发现必须修改的问题”，不要为了凑数量输出低价值建议。
```

## 多模型审查时的聚合规则

如果使用多个 AI 模型交叉审查，不要简单拼接所有结果。应按可信度聚合。

推荐规则：

| 类别 | 含义 | 处理方式 |
|---|---|---|
| 共性 P0/P1 | 多个模型都发现的高风险问题 | 优先展示，通常可信度最高 |
| 单模型 P0 | 只有一个模型发现，但风险严重 | 展示，但标注需要人工确认 |
| 共性 P2 | 多个模型都提到的维护性问题 | 可展示，但放在后面 |
| 单模型 P2/P3 | 低风险或风格类建议 | 默认折叠或不展示 |
| 冲突判断 | 一个模型认为有问题，另一个模型认为没问题 | 展示证据，要求人工判断 |

聚合时应去重：

```text
同一文件、同一行、同一风险类型的问题应合并，不要重复展示。
```

## 高采纳率 Review 的判断标准

一条高质量 AI review 评论应该满足：

- 能定位到具体代码
- 能说明触发场景
- 能说明真实后果
- 能给出可执行修改建议
- 和本次变更直接相关
- 不依赖个人风格偏好
- 开发者看完知道要不要改、怎么改

低质量评论通常表现为：

- “建议优化”
- “建议增加注释”
- “这里可能有问题”
- “代码可读性有待提升”
- “可以考虑重构”
- 没有说明风险和触发条件

## 设计 code review Skill 时的建议

### 1. 默认模式应是 MR 风险审查

默认不要做泛代码审查。默认 prompt 应面向合入风险。

```text
默认模式：mr-risk
目标：判断本次变更是否存在合入风险。
```

### 2. 支持审查模式

可以按场景提供不同模式：

| 模式 | 重点 |
|---|---|
| `mr-risk` | 正确性、回归、数据、安全、测试 |
| `security` | 注入、越权、敏感信息、权限边界 |
| `performance` | SQL、缓存、循环调用、分页、锁 |
| `test` | 测试缺口、边界用例、回归用例 |
| `maintainability` | 复杂度、重复、可演进性 |

### 3. 引入项目规则

通用审查不够时，应加入项目特定规则：

- 团队历史 review 评论
- 项目编码规范
- 常见事故复盘
- 数据库规范
- 测试规范
- API 兼容性规范

这类内容适合放在 Skill 的 `references/` 中，而不是全部塞进 `SKILL.md`。

### 4. 明确低价值建议过滤

Prompt 中应明确：

```text
不要为了凑数量输出低价值建议。
没有 P0/P1 问题时，可以明确说没有发现必须修改的问题。
```

这条很重要。很多 AI review 质量低，不是因为模型找不到问题，而是因为它“必须输出点什么”。

## 最重要的记忆点

AI code review 的目标不是“让代码看起来更好”，而是：

> 发现本次变更中最可能影响正确性、稳定性、安全性、性能和可维护演进的真实风险。

如果一个 review 建议不能说明触发条件和影响后果，它大概率不应该作为高优先级问题输出。
