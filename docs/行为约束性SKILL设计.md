# 行为约束型 SKILL 设计范式

> 行为约束型 SKILL 不主要解决“助手会不会做某件事”，而是解决“助手在做事时是否按正确协作方式执行”。它应被设计成可触发、可执行、可中断、可验证的行为契约。

---

## 一、定义

行为约束型 SKILL 是约束助手执行方式的 SKILL。它不提供领域工具或业务知识，而是规定默认行为、允许例外、禁止行为、失败恢复、输出契约和验收标准。

典型目标：

- 减少不必要确认。
- 防止把过程状态当最终答复。
- 防止任务执行过程中目标漂移。
- 强制关键场景下的安全边界。
- 标准化团队协作方式。

与功能型 SKILL 的区别：

| 维度 | 功能型 SKILL | 行为约束型 SKILL |
|---|---|---|
| 核心问题 | 做什么 | 怎么做 |
| 主要输入 | 文件、接口、数据、工具参数 | 用户意图、协作场景、风险边界 |
| 主要输出 | 处理结果 | 符合契约的行为过程和最终答复 |
| 设计重点 | 流程、脚本、资源、领域知识 | 默认行为、例外白名单、禁止行为、输出契约 |
| 失败策略 | 重试、fallback、降级可用 | 重试、等价替代、失败/阻塞；禁止静默降级 |

---

## 二、核心设计原则

### 1. 先定义默认行为

行为约束型 SKILL 必须先回答：未触发例外时，助手应该默认怎么做。

示例：

```text
默认连续执行，直到形成可交付结果。
```

默认行为要短、明确、可执行。不要写成愿景，比如“提升效率”“更主动”。

### 2. 用白名单定义例外

不要试图列完所有禁止行为。更稳的方式是定义“只有哪些情况允许偏离默认行为”。

示例：

```text
只有满足以下条件之一时，才允许中断：
1. 关键输入缺失
2. 高风险操作
3. 权限边界
4. 用户明确暂停
5. 恢复后仍无可行路径
```

白名单越清晰，执行越稳定。

### 3. 禁止目标漂移

行为约束型 SKILL 最容易出现的问题不是“不执行”，而是“为了完成而改变完成标准”。

必须明确：

- 弱验证不能冒充完整验证。
- 部分实现不能冒充完整实现。
- 近似数据不能冒充权威数据。
- 缩小范围不能冒充满足原始需求。
- 改写用户目标不能冒充成功。

推荐规则：

```text
失败后可以重试，可以使用等价替代，可以明确失败或阻塞；未经用户批准，不能降级完成。
```

### 4. 把行为写成状态机

单纯写“应该主动推进”不够。要写清楚执行阶段。

通用状态机：

```text
识别目标
  -> 收集上下文
  -> 选择路径
  -> 执行
  -> 失败恢复
  -> 验证
  -> 收尾输出
```

状态机的作用是降低解释空间，让不同助手按同一节奏执行。

### 5. 输出契约必须固定

行为约束型 SKILL 的最终输出要稳定，否则用户无法判断任务是否真的完成。

推荐最终输出：

```markdown
**完成项**
- ...

**关键文件**
- ...

**验证结果**
- ...

**阻塞项**
- 无
```

如果中断，也要固定输出：

```markdown
**中断原因**
触发允许中断条件：<条件名称>。

**已完成**
- ...

**需要用户提供/确认**
- ...

**确认后下一步**
- ...
```

### 6. 过程通知不是最终答复

复杂任务需要过程通知，但过程通知只能同步进度，不能成为“停在半路”的理由。

推荐写法：

```text
过程通知可以说明正在检查、修改、重试或验证什么；除非命中允许中断条件，否则不要以“是否继续？”结尾。
```

## 三、推荐 SKILL 结构

行为约束型 SKILL 的 `SKILL.md` 建议使用以下结构：

```markdown
---
name: <skill-name>
description: <触发条件 + 默认行为 + 允许中断边界>
---

# <Skill Title>

## 目标
说明要约束的协作行为。

## 核心规则
一句话定义默认行为。

## 允许例外/允许中断条件
用白名单列出可以偏离默认行为的条件。

## 执行状态机
定义助手应该如何推进任务。

## 恢复策略
定义失败后如何重试、等价替代、报告失败。

## 禁止行为
列出会破坏目标的红线。

## 中断输出格式
定义触发例外时如何向用户说明。

## 最终输出契约
定义完成态答复必须包含什么。

## 常见错误
列出容易违反约束的模式和修正方式。
```

不建议在运行时 `SKILL.md` 中放太多安装说明、设计历史、长篇背景。这些内容可以放到 `INSTALL.md`、`DEVELOPMENT_PLAYBOOK.md` 或 `references/`。

## 四、设计流程

### Step 1：观察行为问题

记录助手的错误行为，而不是直接写规则。

```text
现象：助手在复杂任务中频繁要求用户回复“继续”。
影响：用户被迫多轮确认，任务无法一次完成。
根因：助手把过程通知当成需要用户决策的暂停点。
```

### Step 2：抽象默认行为

把理想行为压缩成一句话。

```text
默认连续执行到可交付结果。
```

### Step 3：定义例外白名单

只允许在少数明确条件下偏离默认行为。

```text
仅在关键输入缺失、高风险操作、权限边界、用户暂停、恢复后仍无可行路径时中断。
```

### Step 4：定义红线

列出最容易破坏质量的行为。

```text
禁止把弱验证当完整验证。
禁止把部分实现当完整实现。
禁止为了完成而改写用户目标。
```

### Step 5：写执行状态机

让规则可执行。

```text
明确目标 -> 收集上下文 -> 执行 -> 恢复 -> 验证 -> 收尾
```

### Step 6：写输出契约

让结果可检查。

```text
完成项 + 关键文件 + 验证结果 + 阻塞项
```

### Step 7：反向测试

用反例检查 skill 是否能挡住坏行为：

- 是否还会问“要不要继续”？
- 是否会用弱验证冒充完成？
- 是否会因为任务长就停？
- 是否会在高风险操作前直接执行？
- 是否能说明中断触发了哪条规则？

## 五、质量评估维度

行为约束型 SKILL 不适合只用功能型指标评估。建议使用以下维度：

| 维度 | 检查问题 |
|---|---|
| 目标清晰度 | 是否一句话说明要约束什么行为 |
| 触发准确性 | description 是否覆盖真实触发场景和显式调用 |
| 默认行为 | 是否明确未触发例外时必须怎么做 |
| 例外白名单 | 是否清楚列出允许中断/允许偏离的条件 |
| 禁止行为 | 是否列出破坏质量的红线 |
| 失败恢复 | 是否区分重试、等价替代、失败/阻塞 |
| 防降级 | 是否禁止未经批准降低验收标准 |
| 输出契约 | 是否定义最终答复和中断答复格式 |
| 可验证性 | 是否能通过反例判断是否遵守 |
| 可移植性 | 是否避免绑定单一工具或单一团队习惯 |

## 六、continuous-execution-guard 设计要点

该 skill 的关键不是“让助手更努力”，而是明确：

```text
默认继续执行；只有命中白名单条件才中断；失败后不能静默降级。
```

好的版本必须包含：

- 默认连续执行。
- 过程通知不等于最终答复。
- 允许中断条件白名单。
- 失败恢复策略。
- 禁止静默降级。
- 固定最终输出契约。
- 固定中断输出格式。
- 复杂度分级和中断预算。

## 七、常见反模式

### 反模式 1：只写愿景，不写执行规则

```text
让助手更主动。
```

问题：不可执行、不可验证。

改成：

```text
除非命中允许中断条件，否则持续执行到完成态结果。
```

### 反模式 2：只写禁止，不写允许例外

```text
不要频繁中断。
```

问题：助手不知道什么时候可以中断。

改成：

```text
只有关键输入缺失、高风险操作、权限边界、用户暂停、恢复后仍无可行路径时允许中断。
```

### 反模式 3：把 fallback 当成万能恢复

```text
失败后使用替代路径。
```

问题：替代路径可能降低任务质量。

改成：

```text
失败后可以重试或使用等价替代路径；如果只有弱化路径可用，必须报告阻塞或请求用户批准降级。
```

### 反模式 4：最终输出不固定

问题：用户无法判断是否完成、改了什么、验证了什么。

改成：

```text
最终输出必须包含完成项、关键文件、验证结果、阻塞项。
```

## 八、最小模板

```markdown
---
name: <behavior-skill-name>
description: <行为约束目标>。Use when <触发场景>。除非命中 <允许例外>，否则 <默认行为>。
---

# <Skill Title>

## 目标
<说明要修正的行为模式和期望协作方式。>

## 核心规则
<一句话默认行为。>

## 允许例外
- **<例外 1>**：<定义>
- **<例外 2>**：<定义>

## 执行状态机
1. <阶段 1>
2. <阶段 2>
3. <阶段 3>

## 禁止行为
- <红线 1>
- <红线 2>

## 输出契约
```
**完成项**
- ...

**验证结果**
- ...

**阻塞项**
- 无
```
```
